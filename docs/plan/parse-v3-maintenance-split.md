# 解析规则 v3：汇总公告按条目切分

状态：方案，未实施。目标文件是 `internal/stellasora/`（规则）与 `internal/annsync/`（投影与去重），
不改 QQ 侧、不改存储桶结构、不改 `cmd/` 组装点。

## 1. 要解决的问题

版本首日的**维护更新说明**（《星塔旅人》09月08日维护更新说明 那一类）正文里，把整个版本从开
始到结束的全部活动档期一次性列完，包括版本后半段那些**还没有独立公告**的活动。当前解析器把
这类公告整条丢弃，所以日历在版本开始后约两周内，后半段是空的。

实测依据（2026-09-07，`.probe/caladv`，判据为窗口交并比 ≥0.8）：

| 公告 | 发布 | 正文档期 | 库里已有 | 库里拿不到 | 独立公告比它晚发的 |
|---|---|---|---|---|---|
| 4550《09月08日维护更新说明》 | 09-07 18:00 | 12 | 8 | **4** | — |
| 4379《08月18日维护更新说明》 | 08-17 18:00 | 14 | 13 | 1 | **5** |
| 4008《07月21日维护更新说明》 | 07-20 18:00 | 21 | 19 | 2 | **7** |

4550 拿不到的那 4 个正是后半段：终焉绝响 09/22 12:00~09/28 22:59、其排名奖励领取 09/30~10/30、
命运星牌局 09/22 12:00~09/29 10:59、紧急悬赏 09/22 04:00~09/29 03:59。提前量中位 11.7 天、最大
21.8 天。全库共 19 条公告被这条规则丢弃，合计 100 个主时间窗口。

同一份正文还顺带解决了另外两个已知缺口：

- **版本窗口边界要人工锚**。现在出图用的三个版本窗口是手抄的，因为 `redeem`（兑换截止）写在
  「活动商店与奖励兑换时间」行里，被 `secondaryRe` 当附属窗口丢了。
- **角色名/属性/星级/池类型没有结构化字段**。正文 `✦ 全新旅人与秘纹` 那段就是它们的文字版：
  `新增全新风属性五星旅人「埃莉诺」，可通过参与限时招募活动「优雅起舞 千金驾到」获得`。

## 2. 现状：丢弃发生在哪两行

```go
// internal/stellasora/parse.go  Result.Suspect()
if len(r.Primary) > 1 {
    return true                       // 只影响「待确认」展示，不是丢弃点
}

// internal/stellasora/source.go  Source.Fetch()
if len(res.Primary) != 1 {
    return item, nil                  // ← 真正的丢弃点：0 个和 >1 个都不产 Events
}
```

规则 v2 的注释说得很清楚：「剩下的主窗口必须恰好一个才采信；多了说明这是条汇总公告，整条交人
工，不猜」。这个判断对**单活动公告**是对的——一条公告讲一个活动，出现两个主窗口确实只能靠猜。
错在把同样的判据套到了**汇总公告**上：汇总公告的多个主窗口不是"二选一"，而是"N 条记录"，正文
里每一条自带活动名，本来就不需要猜。

## 3. v3 规则

### 3.1 公告先分三类，再谈采信

| 类别 | 判据 | 产出 |
|---|---|---|
| 单活动公告 | 标题第一对「」能取到名字，且 `len(Primary) == 1` | 1 条事件（现状不变，`Provenance="solo"`） |
| 版本窗口公告 | 标题匹配 `^\[[^\]]{2,40}\](活动\|版本)一览$` | 1 条**版本窗口**记录，不是活动，不进日历 |
| 汇总公告 | `len(Primary) + len(Secondary) >= 2` 且条目切分能拿到 ≥1 个具名条目 | N 条事件（`Provenance="summary"`） |

**单活动路径必须要求 `Name != ""`。** 现状是 `len(Primary) == 1` 就产事件，名字为空时由
`sync.go` 回退成公告标题，于是 4118《07月31日在线闪断更新》正文里那句
`活动时间：2026-08-01 04:00 ~ 2026-08-31 03:59`（补偿邮件的有效期）被解析成一条横跨整月的
"活动"。加上这个条件后它自然不产出——公告标题没有「」，本来就不是活动公告。

但这个条件有一处**实测例外**，不能一刀切：2115《星塔旅人》H5趣味网页活动里程碑奖励，标题用的
是书名号不是引号，正文却实打实只有一个主窗口，是条真活动公告。所以判据要写成两条：

```go
case Name != "" && len(Primary) == 1:                            // 常规
case Name == "" && len(Primary) == 1 && strings.Contains(Title, "活动"):
    // 标题没用「」但确实是活动公告；名字用标题剥掉《游戏名》前缀
    Name = strings.TrimSpace(gamePrefixRe.ReplaceAllString(Title, ""))
```

只按"标题含活动"收，4118 那类（标题是「在线闪断更新」）仍被挡在外面。

**版本窗口公告抽不出边界时不要报警。** 实测 `[XXX]活动一览` 与 `[XXX]版本一览` 是两条不同公告：
前者正文有文字档期（能抽出 act0/act1/redeem），后者**整篇是一张图**（3984/4357/4541 三条，
`Primary` 与 `Secondary` 均为 0）。同版本的边界由前者给出，所以 `Ver == nil && 零窗口` 属已知形状，
报警只会淹没「待确认」桶。

三类都不满足 → 维持现状，不产事件；`Suspect()` 的第二个分支（有名字、零窗口、正文长得像有档期）
保持不变，那是"日期画在图片里"的报警，跟本方案无关。

`Suspect()` 第一个分支改为：**汇总公告切分失败才报警**。即 `len(Primary) > 1 && len(Entries) == 0`。
切分成功的汇总公告不再进「待确认」桶——它现在是被采信的数据源，塞进人工桶只会淹没真正需要人看的。

### 3.2 条目切分（新增 `splitEntries`，纯函数）

正文形状（4550 原文，去掉 HTML 后）：

```
✦ 全新活动
- 终焉绝响
活动时间：2026/09/22 12:00 ~ 2026/09/28 22:59
排名奖励领取时间：2026/09/30 04:00 ~ 2026/10/30 03:59
活动说明：参与联合作战，累积伤害，登上排行榜！…
参与条件：权限等级≥10
```

一个条目块 = 一条条目行 + 其后直到下一条条目行之间的所有窗口行。

**条目行判据**（三条同时成立）：

1. 以 `-`、`–`、`—`、`*`、`■`、`✦` 之一开头（与现有 `tagOf` 的 `TrimLeft` 字符集同源，不新造一套）；
2. 去掉引导符与空白后，长度 2~40，且**整行不含** `intervalRe` 可匹配的窗口（含窗口的行是窗口行）；
3. 不命中字段行黑名单：`^(活动说明|参与条件|售卖价格|礼包内容|版本限购|获取方式|内容说明|备注|\*)`。

第 3 条是防误伤的关键：礼包段里 `- 午后茶会·特惠礼券组合` 是真条目，紧跟的 `礼包内容：青空礼券*10`
不是；而 `✦ 限时商品` / `✦ 全新旅人与秘纹` 这类小节行虽然像条目，但块内没有窗口行，被"块内必须有
窗口才产出"兜住。

**条目名取法**，按优先级：

1. 行内有 `限时招募活动「(.+?)」` → 取捕获组，且**同一块内出现几个就产几条事件、共用该块窗口**。
   这是 4550 的 `招募时间` 那条：两行分别给出角色池「优雅起舞 千金驾到」与秘纹池「飞向梦寐以求的
   世界」，共用同一个 `2026/09/08 维护结束后 ~ 2026/09/29 10:59`。若只取第一对「」会得到角色名
   「埃莉诺」，那是旅人不是活动。
2. 否则取行内第一对「」；
3. 否则取去引导符后的整行（截断到 40 字）。

**窗口归属与标签**完全沿用 v2：`tagOf` 行内前缀优先于 `▌小节标题`，`secondaryRe` 命中的进
Secondary 并丢弃。所以「排名奖励领取时间」「活动商店与奖励兑换时间」「售卖时间」照旧不产事件。

产出结构：

```go
// parse.go
type Entry struct {
    Name  string
    Label string      // 时间标签，同 Interval.Tag
    Ival  Interval    // 复用，含 Start/End/Status/Line
}

type Result struct {
    ...
    Entries []Entry   // 汇总公告的条目切分结果；单活动公告为空
}
```

### 3.3 版本窗口公告（新增一类产出）

`[XXX]活动一览` / `[XXX]版本一览` 正文固定两行（三条实测同形状）：

```
活动时间：2026/08/18 维护结束后 ~ 2026/09/01 03:59          → act0, act1（玩法期止）
活动商店与奖励兑换时间：2026/08/18 维护结束后 ~ 2026/09/08 10:59 → redeem（版本终点）
```

第二行现在被 `secondaryRe` 丢弃，所以 `redeem` 只能人工锚。v3 对这一类公告**不走"丢弃附属窗口"
的常规路径**，而是直接产出：

```go
type VersionWindow struct {
    Name           string    // 方括号里的版本名
    ActStart       time.Time
    PlayEnd        time.Time // 玩法期止
    RedeemEnd      time.Time // 版本终点：兑换截止
    SourceID, RefID string
}
```

它不是活动，因此**不进 `activity/` 桶、不进内存日历**，单独存 `version/<src>:<id>`。
这样 `calendar` 查询行为完全不变，出图层和将来的"版本"命令才用得到它。

注意 4541《[奋斗吧！…]版本一览》与 4540《[奋斗吧！…]活动一览》是同版本的两条公告，会产出两条
VersionWindow。以 `RedeemEnd` 最大的那条为准，其余保留但不参与窗口计算（见 §4 的键设计）。

### 3.4 投影：谁的名字、谁的图

`sync.go` 投影时现有两条回退：

```go
title := ev.Title;  if title == "" { title = it.Title }       // ← 汇总页会回退成公告标题
poster := ev.Poster; if poster == "" { poster = it.Thumbnail } // ← 维护公告的封面是运营图
```

v3 要改第二条：**`Provenance == "summary"` 的事件不回退 `it.Thumbnail`**，海报留空。维护公告的
列表封面是《星塔旅人》logo 那一类通用图，填进去等于给每个活动配同一张假海报，比没有更糟。
出图侧要能容忍空海报（渲染成占位）。

第一条不改：条目切分产出的 `ev.Title` 一定非空，走不到回退分支。

### 3.5 去重：实现星塔源的 `Merger`

`types.go` 的注释写着「星塔源用它把版本公告与独立公告的重复子活动并成一行」，但 `stellasora`
包里**没有 `Merge` 实现**，`Provenance` 全库 177 条为空。本方案把它补上，顺带让 `Provenance` 真
正被赋值。

星塔源实现 `Merger.Merge(all []Item) []Item`，在投影前对全量条目做跨条合并：

- **键**：`norm(事件名) + "|" + start.RFC3339 + "|" + end.RFC3339`，`norm` 去空白与尾部标点。
- **同键多条**：`solo` 优先保留，`summary` 丢弃。
- **名字相同、窗口不同**（官方后来微调了时间）：仍按名字配对——保留 `solo` 的窗口与海报，
  删掉 `summary` 那条，并把 `summary` 的原文行记进 `TwinRef` 便于回溯。
- **只有 `summary`**：保留，海报空。等独立公告发出后的那一轮，`saveRecs` 全量重算自然替换掉它
  （`sync.go` 的投影是"先清本源旧记录再写新记录"，不留孤儿）。

这条"先出档期、后补海报、全程只有一条记录"的路径是本方案的主要收益，也是为什么去重必须做在
投影前而不是靠 `Project` 里那个 `triple{title,start,end}` 兜——那个键要求时间完全相同，而官方
微调时间时恰恰不相同。

  产出**两条**（两个池名）。
- 新增"条目行判据"的反例集：`活动说明：…`、`参与条件：权限等级≥10`、`✦ 限时商品`（块内无窗口）、
  `- 午后茶会·超值闪碟组合`（块内只有价格与限购，无窗口 → 不产出）。
- `pipeline_test.go` 时序用例：第 1 轮只有维护公告 → 日历有终焉绝响、无海报；第 2 轮独立公告到达

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 条目行判据过宽，把说明行当活动名 | 三条判据同时成立 + 字段行黑名单 + "块内必须有窗口行才产出" |
| 汇总公告与独立公告重复，日历出现双份 | `Merger` 按名字配对；`Project` 原有 `triple` 去重作为第二道 |
| 官方后续微调时间，两条记录窗口不同 | 配对以名字为主、时间为辅，`solo` 覆盖 `summary` |
| 维护公告封面被当成活动海报 | `summary` 事件不回退 `it.Thumbnail`（§3.4） |
| 正文改了但标题/发布时间/封面没变，增量轮次漏掉 | 既有盲区，`listHash` 注释已记；靠 `FullEvery` 全量校准轮兜。本方案不新增也不修复它 |
| 官网换版式，条目形状变了 | `SplitSummary` 开关退回 v2；`Weird` 桶（含日期却没认出窗口的行）会涨，是现成的报警面 |

## 7. 实施顺序

1. `splitEntries` + `Result.Entries` + 4550 fixture 测试（纯函数，零 IO，可独立合入）；
2. `Fetch` 三分派 + `Provenance="summary"`，跑全库 19 条被丢弃公告，人工核对产出条数；
3. `Merger` + 投影不回退海报，跑 `pipeline_test` 的时序用例；
4. `VersionWindow` 与 `version/` 桶（出图层依赖，可与 1~3 并行）；
5. 观察一个完整版本周期（约 3 周）后再考虑把 `summary` 来源用于到期提醒——到期提醒会主动推送，
   数据可信度要求比日历展示高一档，先只喂日历。

## 8. 实测结果（2026-09-07，`.probe/calgen`）

按本方案实现的 v3 解析器（`.probe/calgen/parse.go`，独立实现，未碰 `internal/`）跑了官网全量
**349 条公告正文**（并发 4 抓取，13 秒，正文缓存在 `.probe/calgen/body/`）：

```
事件 181 条（独立公告 173 + 汇总公告切出 8，去重丢弃 99，版本名重复滤掉 6）
海报内联 38 张，取不到图 0 张
版本窗口 3 个；周期玩法 3 种（创业激励基金、猎影合围Beta、联合讨伐）
切分失败报警 0 条
```

按「同名 + 窗口交并比 ≥0.8」配对成功被丢弃，6 个撞上版本名被滤（其中 1 个是误杀，见 §9.1），
净新增只有 8 个——都是独立公告还没发的。

`cut`（兑换领奖尾段）现在全库只剩 4156 一条，判据见 §9.4。留档在
`.probe/calpng/keep/v3-2026-09-07/`（页面、模板、data.json、解析器、运行日志各一份）。

### 8.1 这套实测暴露的两处方案外信息

4550 的 `✦ 全新旅人与秘纹` 段里，**一个 `招募时间` 窗口对应两个池子**（角色池 + 秘纹池），
条目切分必须"一窗口多名"。方案 §3.2 已按此实现，实测正确产出两条。
若沿用"一行一个活动名"的直觉实现，会漏掉秘纹池。

另一处见 §9.1——版本名过滤器把主活动一起滤掉了，是实测才发现的。

## 9. 已知缺陷（实测发现，均未修）

### 9.1 版本名过滤器误杀同名主活动

维护公告会把版本本身列成一个「开放时间」条目（4379 的「欢歌劲浪·闪耀假日惊涛探险！」），
与版本窗口重复，所以 §8 加了一条按版本名过滤的规则，滤掉 6 条。

但**有些版本的版本名同时就是主线活动名**。4550 里「奋斗吧！大小姐的旅人修炼手册！」出现三次：

```
✦ 全新剧情
- 限时活动剧情故事「奋斗吧！大小姐的旅人修炼手册！」
开放时间：2026/09/08 维护结束后 ~ 2026/09/22 03:59      ← 该滤

✦ 全新活动
- 奋斗吧！大小姐的旅人修炼手册！
活动时间：2026/09/08 维护结束后 ~ 2026/09/22 03:59       ← 不该滤，这是主活动本体
活动商店与奖励兑换时间：2026/09/08 维护结束后 ~ 2026/09/29 10:59
```

现在两条都被滤，导致下一版本视图缺了主活动。两个修法：

- **方案 C（推荐，不依赖分组名）**：版本名条目只有在"该名字下找不到 `活动商店与奖励兑换时间`
  行"时才滤。有兑换商店的就是活动本体——4550 的奋斗吧有兑换行 → 保留；4379 的欢歌劲浪只有
  开放时间 → 滤掉。语义准确，且兑换行本来就在 `Secondary` 里，不需要新解析。
- 方案 A：`Entry` 记录所属 `✦` 分组名，过滤条件收紧为 `vnames[norm(name)] && group != "全新活动"`。
  依赖分组标题文案稳定，官网改词就失效。

### 9.2 时间标签为空的窗口被当成主窗口

4 条记录 `lb` 为空，典型是 2115：

```
✧每个账号仅限领取一次奖励；兑换码有效期为【2025/12/09 维护结束后 ~ 2025/12/23 03:59】…
```

`inlineTagRe` 要求标签在行首，而这行以 `✧` 开头、"有效期"在句中且前面有"；"截断 → 标签取成空 →
`secondaryRe`（含"有效期"）无从命中 → 落进 `Primary`。**v2 同样产出了它**，不是 v3 引入的。
可选处置：窗口行标签为空时降级进 `Weird`（报警但不进日历），代价是漏掉真没写标签的真活动。
影响面只在 2025 年历史条目，三个版本视图里看不到，暂不动。

### 9.3 现在 `summary` 来源的记录没有海报（但素材其实已经在 CDN 上）

当前实现里海报只认独立公告的列表封面，而独立公告要等版本过半才发（实测提前 1~3 天），所以
维护公告补出的那批档期只能是斜纹占位。

**但这不是必然的**：实测发现同版本的 `[XXX]版本一览` 公告（4541）比给档期的维护公告（4550）
还早 31 小时，正文里带着全版本活动的 banner 图，且图床的服务端裁切可用。也就是说图与档期都能
在版本更新前拿全，缺的只是"从分组竖长图里把单张 banner 切出来并配对"这一步。方案见 §10 T3。

**2026-09-07 CDN 实测更新：这条"补海报"的路基本走不通，T3 从关键路径摘除。**

- **干净单张不可寻址**：图片桶 `webusstatic.yo-star.com`（OSS `webusstatic.oss-us-east-1`）、
  `nova-static.yostar.cn`（OSS `nova-prod-static.oss-cn-shanghai`）、站点静态资源 `webcnstatic.yostar.net`
  （Tengine CDN）**三个主机匿名列举全 403**；对象 key 是 8 位随机哈希，不可猜。→ "先试 ListObjects
  拿官方未拼长的单张 banner"（T3 第 5 步）落空。
- **合成长图自动切分不可靠**：在最高的那张（1000×3613）上按行扫纯色带，只切出 2 段（该段实含 ~5 个
  活动），banner 之间没有干净分隔带。→ T3 第 1 步（色带分段）证伪。
- **未发独立公告的新活动（如「优雅起舞 千金驾到」埃莉诺卡池）在发公告前无任何干净图源**，只能占位。
- **但版本级横幅是现成可取的**：首页滚动横幅那张（埃莉诺举奖杯 + "版本内容一览"）就是 4541 的
  `thumbnail`（`…/2026/09/04/NmoIKsT8.jpg`），news API 对每条**已发布**公告都返回 thumbnail，
  直接可取、不需裁图。可作整个版本的头图/占位。
- **复玩模式可借上期封面**：终焉绝响/命运星牌局/紧急悬赏/甜心梦工坊 都是周期复玩，过去每期有独立公告
  + 干净封面；但**每周期重做主打角色与背景**（实测两期终焉绝响封面标题版式一致、画面不同），属"认得出
  玩法但错周期"的近似图，只适合小格子。
- **台服不是新门**：国服站的图现在就存在海外 YoStar 桶（`webusstatic.yo-star.com` / us-east-1）上，
  台服公告图几乎必然走同一共享桶，同样不可列举。（台服域名本次未探明，不作断言。）
- **结论**：海报缺口是**纯装饰且会自愈**——独立公告在活动开始前 1~3 天发，届时 `Merger` 的 solo 自动
  补上准确封面；档期（功能本体）维护公告已经给了。v3 不必带海报方案落地。

### 9.4 兑换尾段判据（已修，记录口径）

最初写成"终点压在版本兑换截止就裁"，结果把卡池与灾变防线也裁了——它们招募/开放到版本结束是
**真档期**。收紧为"起点早于本版本 act0 且终点 == redeem"后，全库只剩 4156 一条命中，符合预期。
另一个坑：不能用"按起点找归属版本"来定位它属于哪个版本——4156 起点在上一个版本里，按起点匹配
不到，必须直接遍历版本表。

### 9.5 生产侧还看不到这些增益

4550 发布 09-07 18:00，同步器 `LastSuccess 09-07 14:25`，所以它连 `Item` 都还没进库；
即便进了，现行 `source.go` 的 `len(res.Primary) != 1` 也会把它整条丢掉。上面所有数字都来自
`.probe/calgen` 的模拟件，生产日历要等 §4 的改动落地。

### T3 从 CDN 拿活动素材（2026-09-07 实测：基本走不通，已摘除；以下保留作记录）

> **更正指针**：下面"三条结论"与 ListObjects / 分段裁切步骤是动手前的假设，事后被 §9.3 的实测推翻
> （三主机列举全 403、色带分段不可靠）。只作过程留档，勿据此实施。

`.probe/calgen/probe-img.js` 实测结果（2026-09-07）：

```
4541《[奋斗吧！大小姐的旅人修炼手册]版本一览》  发布 09-06 11:00   正文 9 张图
  413x250（列表封面）  1920x1080（版本主视觉）
  1000x3613  1000x2407  1000x2927  1000x2038  1000x2927   jpg
  1000x2031  1000x2125                                      gif
4357《[欢歌劲浪·闪耀假日惊涛探险！]版本一览》  发布 08-15 前后    正文 7 张图
  413x250  1920x1080  1000x6392  1000x3760  1000x3801  1000x1932(gif)  1000x5747
16 张全部：?x-oss-process=image/crop,w_600,h_338/resize,m_lfit,w_300/quality,q_62/format,jpg → HTTP 200
```

三条结论，都跟这个方案之前的假设不同：

1. **不是一张长图，是按分组切开的 7~8 张 1000 宽竖长图**（高 2000~6400），每张里堆若干个活动的
   banner。所以"裁切"要处理的是 2~4 段的短序列，不是一整版。
2. **服务端裁切可用**（16/16 返回 200），不需要任何本地图像库或游戏资源包。
3. **版本一览比给档期的维护公告还早**：4541 发布 09-06 11:00，4550 发布 09-07 18:00，早 31 小时。
   也就是说**下一版本的图与档期都能在版本更新之前拿全**，`summary` 记录"注定没海报"这个结论是错的
   （§9.3 已更正）。

剩下的唯一难点是"把 banner 从竖长图里切出来并与档期配对"。可行路径：

1. **分段**：下载长图，逐行扫描找接近纯色的分隔带，得到若干 banner 段。Go 标准库
   `image/jpeg` / `image/png` / `image/gif` 足够解码取像素，仍然不需要 `x/image`。
   `.probe/calgen/main.go` 里的 `washFromImage` 已经在做同类像素访问，可复用。
2. **用分组对齐**：段数应当等于该分组下的活动条目数，而分组标题与条目顺序维护公告里都有
   （`✦ 全新活动` 下 5 条 → 对应那张 1000x3613 里的 5 段）。两侧都有序，直接 zip 配对。
3. **只存裁切参数，不存图**：把 `图片URL + y 偏移 + 高度` 记进记录，出图时拼
   `?x-oss-process=image/crop,y_<n>,h_<n>/resize,...` 的 URL 即可。只有 QQ 发图那条路才需要
   真下载字节流（见 T6）。
4. **兜底**：分段数与条目数对不上时，退回现在的斜纹占位，不要瞎配。
5. **先试一次 ListObjects**：`https://webusstatic.yo-star.com/?list-type=2&prefix=web-cms-test/upload/content/2026/09/`。
   若公共读桶允许匿名列举，可能直接拿到官方未拼长的单张 banner，省掉整个裁切环节。
   预期是 403，但一个请求就能判定，应该先试再动手写分段。
6. 游戏客户端资源包（版权、体积、跟版本更新）成本最高，放最后。
